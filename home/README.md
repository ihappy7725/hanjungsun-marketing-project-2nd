#### 카드 중요도 표현 방식 결정 (2026-10-25)

박스 중요도를 색 농도로 구분하거나 편집 모드로 크기를 조정하는 안을 검토했으나 채택하지 않았다. 색 농도는 공통 디자인 체계와 충돌하고 글자 대비를 해치며, 중요도가 상황에 따라 바뀌는데 색은 고정된다. 편집 모드는 드래그 조정·크기 저장·반응형 대응까지 필요해 비용이 크다.

- **채택한 방식:** 위계는 배치(캘린더가 가장 크고 왼쪽 위, 뉴스가 왼쪽 아래, 보조 카드 넷이 오른쪽)로 표현하고, 색 대신 상태에 반응하는 신호를 더한다.
- **지연 배지:** 현재 선택한 캠페인에 마감일이 지난 미완료 업무가 있으면 진척 카드 제목 옆에 '지연 N건' 배지를 빨간색으로 띄운다. 지연이 없으면 배지를 표시하지 않는다. 고정 장식이 아니라 문제가 있을 때만 눈에 띄게 하기 위해서다.
- 배지의 기준은 진척도와 같은 현재 캠페인 업무다. 취소 업무는 진척도와 마찬가지로 제외한다.

#### 주 보기 타임라인 · 상단 시계 · 뉴스 표시 정리 (2026-10-25)

주연의 지시로 캘린더 주 보기를 시간 타임라인으로 바꾸고, 상단 기준일 입력을 시계로 교체했으며, 뉴스 표시를 줄였다. 아래 4·5·7.3장의 화면 설명 중 이 메모와 어긋나는 부분은 이 메모를 우선한다.

- **업무 시간 등록:** 업무에 `due_time`(`HH:MM`) 칸을 추가했다. 업무 수정 창의 '시간' 칸에 입력하며 비우면 종일 업무다. 형식이 맞지 않으면 빈 값으로 저장한다. 기존 업무에는 시간이 없으므로 모두 종일로 표시된다. 타임라인 칸을 누르면 그 날짜가 선택되고 오늘의 해야 할 일 목록이 그 날짜로 바뀐다.
- **상단 시계:** '업무 기준 · 한국 UTC+9' 날짜 입력과 '실제 오늘' 버튼을 없애고 한국·베트남 현재 시각을 함께 표시한다. 한국 시각 옆에 '(기준)'을 붙여 업무 기준이 한국 시간임을 밝힌다. 30초마다 갱신한다.
- **기준일 수동 변경 기능 삭제:** 날짜 입력칸이 없어졌으므로 업무 기준일은 항상 실제 한국 날짜다. 화면에서 기준일을 바꿔 D-day·지연 판정을 확인하던 방법은 더 이상 쓸 수 없다. 14.3장의 '명세의 한국 기준일을 화면에서 바꾸어 확인' 설명은 이 메모로 대체한다.
- **연·월 표시:** 캘린더 상단 연·월 글자를 한 단계 키웠다(`--fs-body` → `--fs-subheading`).
- **캘린더 축소:** 날짜 칸 최소 높이를 48px에서 38px로, 기간 막대 최소 높이를 24px에서 20px로 줄였다.

#### 대시보드 화면 재구성 · 오늘의 해야 할 일 (2026-10-24)

주연의 지시로 상단 여백, 캘린더, 업무 영역을 바꿨다. 아래 4장·5장의 화면 설명 중 이 메모와 어긋나는 부분은 이 메모를 우선한다. 저장된 업무·일정 자료와 저장 경계는 바꾸지 않았고 화면 구성만 변경했다.

- **상단 축소:** 제목 영역과 안내 문구의 바깥 여백을 줄여 카드 영역에 공간을 넘겼다.
- **캘린더:** 카드 안 스크롤을 없애고 높이를 내용에 맞췄다. 조회한 기간의 날짜가 잘리지 않고 모두 보인다. 월·주·목록 보기와 기간 막대는 유지한다. 캘린더 아래에 있던 '선택한 날짜' 상세 목록은 삭제했다.
- **업무 영역 분리:** 기존 '업무 진척·해야 할 업무' 카드 하나를 독립된 카드 두 개로 나눴다. 위는 캠페인 업무 진척, 아래는 오늘의 해야 할 일이다.
- **진척도 기준:** 위 카드는 **현재 선택한 캠페인에 속한 업무**만 분모로 쓴다. 상단의 표시 범위 선택(전체/현재 캠페인)은 아래 업무 목록에만 적용하며 진척도에는 영향을 주지 않는다. 취소 업무를 분모에서 제외하는 기존 규칙은 유지한다.
- **오늘의 해야 할 일:** 선택한 날짜가 마감일인 업무를 보여준다. 기본값은 업무 기준일이며, 캘린더에서 다른 날짜를 누르면 그 날짜의 업무로 바뀌고 제목도 함께 바뀐다. 기준일이 아닐 때는 '오늘로' 버튼이 나타난다.
- **완료 표시:** 체크하면 취소선이 그어지고 완료로 표시되지만 목록에서 사라지지 않는다. 그날 무엇을 했는지 함께 보기 위해서다. 체크 해제로 되돌릴 수 있고 캘린더·진척도에 함께 반영된다.
- **이월:** 업무마다 `->` 버튼으로 다른 날짜에 옮길 수 있다. 마감일만 바뀌며 캠페인 목표일과 다른 업무는 그대로다. 이월한 업무는 날짜 고정으로 표시해 재계획에서 되돌아가지 않게 한다. 시작일이 있으면 지운다.
- **삭제한 것:** 미완료·지연·보류·일정겹침 필터 버튼과 '완료 보기' 토글을 없앴다. 5.3의 일정 점검(업무 마감일과 현지 일정이 겹치는지 확인) 기능도 함께 사라졌다.
- **남은 영향:** 마감일이 없는 업무와 지난 날짜의 미완료 업무는 해당 날짜를 직접 선택해야 보인다. 오늘 화면에서는 보이지 않으므로 놓칠 수 있다. 보완 방식은 주연과 별도로 정한다.

#### 과일 시즌의 월 단위 달력 표시 (2026-10-24)

주연의 선택에 따라 월·계절 단위로만 확인되는 과일 시즌을 달력에 표시할 수 있게 했다. 아래 이전 메모의 '현재 로더는 일 단위 일정만 허용한다'는 설명보다 이 메모를 우선한다. 이번 변경은 표시 가능 범위를 넓힌 것이며 실제 과일 자료를 등록하지는 않았다.

- `date_precision`에 `month`를 허용한다. `day`의 기존 규칙은 그대로다. `unconfirmed` 등 다른 값은 계속 거부한다.
- `month`는 **`fruit_season` 종류에만** 허용한다. 공휴일·기념일·지역행사를 월 단위로 등록할 수 없다. 휴무 여부와 행사 개최는 일 단위 확인이 필요하기 때문이다.
- `month`는 시작일이 그 달의 1일, 종료일이 그 달의 마지막 날이어야 한다. `2027-04-07~2027-05-23` 같은 달 중간 날짜는 거부한다. 원문이 월까지만 밝힌 기간에 임의의 시작일·종료일을 붙이지 않기 위해서다. 저장된 1일·말일은 달 경계를 나타내는 값이며 수확 시작일·종료일이 아니다.
- 화면은 `2027-04 ~ 2027-05`처럼 달까지만 표시하고 `월 단위 · 일 단위 미확인` 배지를 붙인다. 현지 기회 카드와 일정 상세가 같은 함수를 쓰므로 두 곳에 함께 적용된다. 원문 기간 표현은 `original_period`에 그대로 남긴다.
- 월 단위 자료도 등록 요건은 동일하다. 생산지·품종·원문 기간·독립 교차 출처 2개가 필요하며, 통상 제철과 특정 연도 전망을 구분한다. 제철 정보만으로 OEM 공장의 실제 조달 가능성이나 냉동 원료 공급 기간을 확정하지 않는다.
- 기존 보류 후보 `vn_danang_mango_season_2027`은 근거 부족 상태 그대로이며 이번 변경으로 등록되지 않았다. 등록하려면 베트남 농업기관 자료의 재조사와 독립 교차 확인이 필요하다.

#### 정부 원문 기준 확대 · 2026~2027 공휴일 등록 (2026-10-24)

**이번 작업 범위:** 관리 명령의 출처·분류 검사 수정, 실제 일정 2건 등록, 보류 후보 1건 재확인, 협업 빈 목록 문구 수정, 로컬 DB 초기화다. 같은 날짜의 아래 메모와 충돌하는 부분은 이 메모를 우선한다.

- **정부 원문 도메인 확대:** 1차 출처 검사를 `.gov.vn` 단일 조건에서 `gov.vn`·`chinhphu.vn`·`quochoi.vn`과 각 하위 도메인 허용으로 바꿨다. 베트남 법령 포털(`vanban.chinhphu.vn`, `datafiles.chinhphu.vn`)이 `.gov.vn`이 아니어서 기존 등록 일정 2건조차 이 검사를 통과하지 못했고, 실제 정부 원문으로 등록할 수 없었다. 호스트가 정확히 일치하거나 `.`로 구분된 하위 도메인만 인정하므로 `chinhphu.vn.example.com` 형태는 거부한다. 이는 형식 검사이며 게시 내용의 권한·적용 범위를 보증하지 않는다.
- **연휴 보상 근무일 분류:** `classify()`가 일정명에 `working day`가 있으면 `review_required`를 반환한다. 제공업체가 보상 근무일을 `observance`로 주어 `anniversary_candidate`로 올라오던 문제를 막는다. 2026년 조회의 `Working day for New Year Holiday`(01-10), `Working day for Independence Day Holiday`(08-22)가 해당하며, 쉬는 날이 아니라 출근하는 날이다. 마케팅 판단에 쓸 수 있으므로 자동 제외하지 않고 사람 확인 대상으로 둔다. 2027년 조회에는 해당 항목이 없었다.
- **등록한 일정 2건:** `vn_culture_day_2026`(2026-11-24, 공휴일)과 `vn_national_day_2027`(2027-09-02~09-05, 공공부문 기준 연속 휴무)이다. 문화의 날은 Nghị quyết 28/2026/QH16 제2조 제1항으로 신설되어 2026-07-01 시행된 전국 유급휴일이며, 2026년 휴무 일수는 정부사무처 공문 10065/VPCP-KGVX 제2항에서 1일로 확정됐다. 11-23과 11-28을 교환해 4일 연휴로 만드는 안은 채택되지 않았다. 국경일은 내무부 공지 11483/TB-BNV(2026-10-09) 기준 연속 4일이며 법정일은 09-02·09-03이다. 공문 10065호는 2027년 설 7일안과 함께 같은 문서에서 확인했다.
- **API 기간과 정부 공지의 차이(중요):** Calendarific가 제공한 기간은 정부 공지보다 짧게 나왔다. 2026년 설은 API 02-16~02-21, 정부 승인 02-14~02-22다. 2027년 설은 API 02-05~02-10, 정부 공지 02-04~02-10이다. 2027년 국경일은 API가 09-02 하루만 제공했다. API가 법정일만 제공하고 주말·대체휴일을 포함하지 않기 때문이다. 등록 날짜는 정부 공지를 기준으로 하고 API 기간을 그대로 옮기지 않는다. 스승의 날(11-20)은 2026·2027년 모두 API 결과에 없었으므로 API 목록을 일정 기준 목록으로 쓰지 않는다.
- **민간 적용 구분:** 공공부문 연속 휴무를 전국 일괄 휴무로 설명하지 않는다. 2027년 설은 사업장이 3개 안 중 하나를 선택해 30일 전까지 통지하고, 국경일은 법정 2일로 09-02과 인접한 하루를 사업장이 정한다. 물류·통관 등 행정 일정과 소비자·거래처 일정이 다를 수 있으므로 `applies_to`와 설명에서 구분한다.
- **보류 후보 재확인:** `vn_danang_christmas_market_2026`만 2026-10-24에 재확인했다. 다낭시 관광 포털의 2026-12-04~12-06 안내는 표시 발행일이 2026-06-05였고, 같은 날 행사장(Ariyana Convention Centre)의 예정 행사 페이지에는 12월 행사 안내가 없었다. 날짜 근거가 관광 포털 한 곳에서만 나와 독립 교차 확인이 되지 않으므로 보류를 유지한다. 공지 부재를 취소 확정으로 해석하지 않는다. 불꽃축제·망고 후보의 확인일은 2026-10-23 그대로다.
- **협업 빈 목록 문구:** `home_main.js`의 협업 요약 빈 목록 안내를 '확인할 협업이 없거나 인플루언서 자료를 불러오지 못했습니다'로 바꿨다. 공개 함수가 오류를 `[]`로 돌려주어 조회 실패와 실제 0건을 구분할 수 없기 때문이다. PM1이 진혁에게 상태 확인 함수를 요청하기로 했고, 함수가 생기면 문구를 다시 구분한다. 일정·뉴스는 HOME 자체 자료라 실패와 0건이 이미 구분되므로 바꾸지 않았다.
- **로컬 DB 초기화:** PM1 안내에 따라 `flask --app app init-db`를 실행해 인플루언서·콘텐츠 스튜디오 테이블을 만들었다. 실행 전에는 테이블이 없어 협업 조회가 실패했고 그 실패가 빈 목록으로 보였다. HOME 테이블은 여전히 정의하지 않는다.
- **공통 `.env` 로딩(PM1 회신):** `python-dotenv`를 `requirements.txt`에 추가하고 `.env.example`에 `CALENDARIFIC_API_KEY`를 넣기로 했다. 머지 후에는 관리 명령을 `bp.cli.command`로 등록해 `flask --app app <명령>`으로 실행하고 모듈 안에서 `load_dotenv()`를 부르지 않는다. 현재 `collect`는 여전히 프로세스 환경변수만 읽으며 `.env`를 읽지 않는다. 전환 시 이 명령이 공통 앱·DB를 초기화하게 되는 점은 PM1과 확인한다.
- **콘솔 인코딩:** 베트남어가 포함된 출력은 UTF-8이 아닌 콘솔에서 형식 오류 메시지로 끝난다. Windows cmd에서는 `chcp 65001`을 먼저 실행한다.

#### 일정 수집·검토·승인 등록 관리 명령 (2026-10-24)

**현재 기능:** `home/event_import.py`를 수동 실행한다. 브라우저를 열거나 달력을 조회해도 API 호출·등록은 발생하지 않는다. 정부 원문과 독립 출처를 사람이 확인하고 승인한 뒤에만 실제 자료를 등록한다. 프로그램은 링크와 체크값만으로 사실을 검증하지 않는다. 이 메모는 아래 이전 단계의 ‘관리 명령 미구현’ 설명보다 우선한다. 이번 구현 중 실제 API 추가 호출·새 일정 등록은 하지 않았다.

```powershell
# 저장소 최상위에서 도움말 확인 (.env 읽기·API 호출·DB 초기화 없음)
.\.venv\Scripts\python.exe -B -m home.event_import --help

# 추가 호출 승인 및 공통 키 설정 완료 후에만 실행: 1회 호출·재시도 없음
.\.venv\Scripts\python.exe -B -m home.event_import collect --year 2026 --request-api

# 담당자가 원문을 대조하여 작성한 검토 JSON 검사·후보 저장 미리보기
.\.venv\Scripts\python.exe -B -m home.event_import stage --input <검토자료.json의_경로>
# 출력 내용을 승인한 뒤 같은 명령 뒤에 --confirm <출력된_토큰> 추가

# 저장된 검토 완료 후보의 실제 등록 미리보기 (아직 파일 변경 없음)
.\.venv\Scripts\python.exe -B -m home.event_import register --candidate-id <후보_ID>
# 실제 등록을 승인한 뒤 같은 명령 뒤에 --confirm <출력된_토큰> 추가
```

- `CALENDARIFIC_API_KEY`는 **실행 프로세스 환경변수**로 받는다. 이 명령은 `.env`를 읽지 않는다. 공통 로딩 방식은 PM1 상준과 별도 협의하며 키 값은 명령문·채팅·JSON·Git에 넣지 않는다. `collect`는 명시적인 `--request-api`가 있을 때 공식 HTTPS 주소로 한 번만 요청하고 리다이렉트·재시도·다른 유료 서비스 대체를 하지 않는다. 429 응답이면 한도 오류로 중단한다. 계정 전체의 잔여량이나 다른 프로그램의 사용량은 이 명령이 관리하지 않으므로 무료 계정을 유지하고 제공업체 사용량도 확인한다.
- API 이름·날짜와 **임시 분류**만 출력한다. 유형이 명확한 national/public holiday는 `holiday_candidate`, observance는 `anniversary_candidate`, 계절·시계 변경은 `excluded_from_marketing_calendar`, 지역·종교·근무일·알 수 없거나 섞인 유형은 `review_required`다. 이 분류는 법정 휴무 여부·연휴 기간·마케팅 적합성을 확정하지 않는다. API 결과 0건과 호출 실패도 구분한다.
- API 원본·오류 본문·키가 포함된 요청 URL은 출력·저장하지 않는다. 미리보기 결과를 파일로 리다이렉트해 장기 보관하지 않는다. API 약관의 저장 제한 때문에, 영구 후보 기록은 사람이 정부·독립 원문에서 다시 확인한 사실과 검증 근거로 작성한다.

**검토 입력 JSON 형식** (입력 파일은 담당자가 준비하며 이 명령이 새 양식 파일을 자동 생성하지 않는다):

| 필드 | 작성 기준 |
| --- | --- |
| `candidate_id` | 중복되지 않는 유지용 문자열 ID |
| `verification_status` | 원문 대조를 마친 경우만 `verified` |
| `registration_status` | `pending_approval` (검증과 등록 승인은 별개) |
| `event` | 기존 `events.json`의 일정 한 건과 같은 필드 구조. 상태는 `verification_status=verified`, `registration_status=pending_approval`. 한국어 이름·베트남어 공식명·날짜·종류·지역·적용 대상·원문 기간·설명·검증 메모·확인일·출처 등이 모두 필요 |
| `review.reviewed_at`, `review.reviewed_by` | 실제 원문 검토일(`event.verified_at`과 동일, 미래일 금지), 검토자 |
| `review.originals_opened`, `dates_match`, `scope_match`, `independent_sources`, `latest_notice_checked`, `conflicts_resolved` | 해당 검토를 실제 완료한 경우에만 각각 `true`. 하나라도 미확인·불일치 미해결이면 등록 불가 |
| `review.comparison_notes` | 두 출처의 연도·날짜·지역·적용 대상 비교와 차이 해결 내용 |
| `review.independence_notes` | 같은 보도자료 재게시가 아닌 독립 근거라고 판단한 이유 |
| `review.latest_notice_result` | 최신 변경·취소 공지 확인 범위와 결과. ‘검색 범위에서 발견 못함’과 ‘변경 없음 공식 확인’을 구분 |

- 주 경계에서 막대를 나누고, 각 구간에 제목을 다시 표시한다. 앞·뒤로 이어지면 화살표와 보조기기용 설명을 제공한다. 월 경계 역시 보이는 주 단위로 잘라 표시하며 원래 기간은 보존한다.
- 같은 주의 기간들이 겹치면 별도 줄에 표시한다. 기간 막대가 개별 업무를 가리지 않도록 주 높이를 확보하고, 긴 달력은 기존 카드 안에서 스크롤한다. 막대 줄을 만드는 데 일 단위 자료를 늘리거나 원본을 변경하지 않는다.

- 목록 보기에서는 전체 시작일~종료일을 한 항목으로 유지한다. 모바일의 기본 목록 보기와 월·주 가로 스크롤도 유지한다. 날짜 칸 전체를 휴일 색으로 채우지 않는다.
- 표시 변경은 브라우저 저장 기록·캠페인 목표일·원본 일정 JSON·DB·다른 탭에 쓰지 않는다.

**“마케터가 오늘 해야 할 일을 고르고, 캠페인 목표일까지 준비가 잘되고 있는지 확인하는 화면.”**

사용자는 한정선을 베트남 다낭에 처음 진출시키고 이후 기념일·시즌 캠페인을 계속 운영하는 **한국 기업의 마케팅 담당자**다. HOME은 자세한 시장 보고서나 협업 전체 명단을 읽는 곳보다, 필요한 일을 발견하고 담당 탭으로 이동하는 업무 시작 화면에 가깝다.

| 마케터의 질문 | HOME의 답 |
| --- | --- |
| 무엇을 준비하고 있고 며칠 남았지? | 선택한 주요 캠페인 이름과 D-n |
| 오늘 무엇부터 확인하지? | 지연·보류·일정 겹침 필터와 다음 할 일 |
| 목표일까지 준비할 수 있나? | 목표일에서 거꾸로 배치한 업무, 달력, 간트 차트 |
| 어떤 외부 일정과 협업을 챙겨야 하나? | 조회 기간에 해당하는 현지 기회, 확인할 협업 |
| 반응을 확인하고 다음 콘텐츠를 만들려면? | 캠페인 KPI 한 줄 요약, 뉴스 적용 제안과 원본 탭 링크 |

### 채택한 세 가지 핵심 구성의 이유

1. **목표일 기준 역산:** 기준일만 정하고 준비 단계를 빠뜨리는 일을 줄인다. 현재는 편집 가능한 템플릿을 제공하며, 사용자가 미리보기 후 확정한다. 단계 완료를 강제하는 승인 시스템은 아니다.
2. **내부·외부 일정 함께 보기:** 내부 업무 마감, 현지 기념일·시즌, 협업 초안·검토·게시일을 같은 달력에서 대조한다. 일정이 겹치면 확인할 이유를 보여주며 자동으로 바꾸지는 않는다.
3. **진척과 지연 신호:** 완료율과 지연·보류·겹침 건수를 먼저 보고 해당 업무를 골라 확인한다. 업무 집중일을 계산하는 로직도 있으나 현재 HOME의 전용 집중일 경고 화면은 노출하지 않는다. 통계·AI 기반 지연 예측은 미구현이다.

### 3.3 HOME의 위→아래 3단 위계

| 위치 | 왼쪽 약 65% | 오른쪽 약 35% |
| --- | --- | --- |
| 상단 제목 | 선택한 주요 캠페인명 + D-n, 한국 기준일, 전체/현재 캠페인 표시 범위 | 별도 업무 추가·새 캠페인 버튼 없음 |
| **Tier 1 · 일정과 마감** | 통합 캘린더 + 선택 날짜 상세 일정 | **업무 진척·해야 할 업무** 통합 카드 |
| **Tier 2 · 캠페인 준비** | **디데이 업무 관리**: 캠페인 선택·다음 할 일·간트·KPI 스냅샷·회고 | 하나의 카드 안에 **현지 기회 / 인플루언서 협업 요약** |
| **Tier 3 · 참고 자료** | 뉴스·트렌드 최신 등록 3건을 가로로 배치 | 좁은 화면에서는 아래로 쌓음 |

같은 행의 카드 높이와 위아래 열 너비를 맞춘다. Tier 1의 기본 데스크톱 높이는 **548px**이며 화면 폭에 따라 조정한다. 좁은 화면은 한 열로 바뀌고 긴 목록은 내부에서 스크롤한다.

**최신 삭제 사항:** 캘린더의 보이는 ‘마케팅 캘린더’ 제목과 **‘업무·캠페인 / 현지 일정·시즌 / 협업 일정’ 필터 줄은 삭제**했다. 세 종류의 데이터는 계속 함께 표시한다. 접근성용 캘린더 이름은 유지한다.

## 4. 통합 캘린더

### 4.1 무엇을 표시하는가

| 일정 종류 | 원본 | 표시 내용 |
| --- | --- | --- |
| 내부 업무 | HOME 업무 | 업무 마감일·완료 상태 |
| 캠페인 | HOME 캠페인 | 목표일 |
| 직접 일정 | 기존 HOME 일정 기록 | 회의 등 저장된 일정 |
| 현지 일정 | 현지조사 | 공휴일·기념일·과일 시즌의 시작~종료 기간 |
| 협업 일정 | 인플루언서 | 초안 제출일·검토 마감일·최종 게시 예정일 |

색으로 종류를 구분한다. 일정 종류별 켜기/끄기 UI는 최신 요청으로 제거했다. ‘전체/현재 캠페인’ 표시 범위와 월·주·목록 전환은 유지한다.

### 4.2 사용 방법

- 이전/다음 기간 이동, 오늘로 돌아오기, 월·주·목록 보기를 제공한다.
- 날짜 칸에는 제목 최대 2개를 줄바꿈해 표시하고, 나머지는 `+N`으로 표시한다. 제목을 말줄임표로 자르는 방식은 쓰지 않는다.
- 날짜를 누르면 카드 아래에 그 날짜의 상세 일정이 나온다. 제목이 길거나 일정이 많으면 카드 안에서 스크롤한다.
- 업무는 ‘열기’, 협업은 ‘협업 보기’로 연결한다. 현지 일정은 현지조사로 이동한다.
- 완료한 업무는 달력의 표시에도 반영한다. 취소 업무는 달력에서 제외한다.
- 과일 시즌은 시작일부터 종료일까지 달력에 표시한다.
- 540px 이하에서는 목록 보기로 시작한다. 월·주 보기를 선택하면 작은 화면 안에서 달력을 가로로 스크롤할 수 있다.

### 4.3 현재 없는 버튼

캘린더의 ‘일정 추가’, ‘이날 업무 추가’는 없다. 체크리스트와 상단의 업무 추가 버튼도 없다. 새 캠페인 진입은 현지 기회의 **`+ 역산 캠페인 생성`**으로 모았다.

기존 직접 일정의 표시·편집 로직과 업무 편집 폼은 남아 있다. 그러나 코드에 폼이 있다는 이유만으로 현재 화면에 신규 업무·회의 등록 버튼이 있다고 설명하면 안 된다.

## 5. 업무 진척·해야 할 업무

### 5.1 위쪽: 완료율과 필터

`완료율 = 완료 업무 수 ÷ 취소를 제외한 업무 수 × 100`으로 계산하고 반올림한다. 업무가 없으면 `0%`, `0/0`이다. 이 값은 매출 성과가 아니라 **등록한 업무의 완료 정도**다.

| 필터 | 표시할 업무 | 누르면 보이는 것 |
| --- | --- | --- |
| 미완료 | 완료·취소가 아닌 업무 | 남은 업무 전체 |
| 지연 | 미완료이고 마감일이 한국 기준일보다 앞선 업무 | 기한 초과 업무 |
| 보류 | 미완료이고 상태가 `blocked`인 업무 | 보류 업무 |
| 일정겹침 주의 | 마감일이 현지 기념일·공휴일·과일 시즌과 겹치는 미완료 업무 | 해당 업무와 겹치는 현지 일정 이름 |
| 완료 보기 | 완료 업무 | 완료 목록과 완료 체크 되돌리기 |

필터 건수는 서로 겹칠 수 있다. 예를 들어 지연되면서 보류인 업무는 두 필터에 포함된다. 노란 겹침 경고 박스를 항상 펼치지 않고 **겹침 필터를 선택했을 때만 사유를 보여준다.**

### 5.2 아래쪽: 체크리스트

- 기본 순서: 기한 초과 → 오늘 마감 → 7일 내 마감 → 이후 마감 → 날짜 없음.
- 각 항목은 업무명, 마감일, 캠페인명, 현재 상태를 표시한다.
- 업무명을 누르면 업무명·시작/마감일·캠페인·상태·중요도·관련 탭·메모를 수정한다.
- 상태: 예정(`todo`), 진행 중(`doing`), 보류(`blocked`), 완료(`done`), 취소(`cancelled`).
- 체크하면 **완료율·체크리스트·달력·간트 차트**가 같은 업무 레코드를 기준으로 함께 바뀐다.
- 완료 보기에서 체크를 해제하면 미완료로 되돌릴 수 있다. 현재 체크 해제는 `todo`로 바꾸며 이전 `doing/blocked` 상태를 자동 복원하지 않는다.
- 긴 목록은 카드 안에서 스크롤한다.

### 5.3 일정 점검의 범위

현재 보여주는 신호는 지연·보류·현지 일정 겹침이다. 기념일 당일의 캠페인 공개처럼 **의도한 겹침**일 수 있으므로 겹침은 검토 신호이며 일정 변경을 강제하지 않는다.

‘오늘부터 7일 뒤까지 하루 마감 3건 이상’인 집중일 계산도 코드에 있다. 다만 **현재 HOME에는 집중일 전용 숫자·카드가 없다.** 초기 신호등 점검 카드와 큰 경고 박스는 통합 과정에서 미노출 상태가 되었다. 협업 일정끼리의 모든 충돌, 업무 소요 시간·의존성·휴일을 고려한 자동 재배치는 아직 제공하지 않는다.

## 6. 디데이 업무 관리

### 6.1 제목과 역할

기존 제목 **‘캠페인 역산 일정’ → ‘디데이 업무 관리’**로 바꾸었다. 목표일까지 준비할 업무와 공개 후 확인할 일을 시간순으로 보는 영역이다. 다른 제목 후보는 ‘캠페인 준비 현황’, ‘캠페인 일정 관리’다. 현재 적용 제목은 ‘디데이 업무 관리’다.

### 6.2 기본 마케팅 템플릿

| 목표일 대비 | 업무 | 관련 탭 |
| --- | --- | --- |
| D-35 | 다낭 현지조사·타깃 가설 정리 | 현지조사 |
| D-28 | 목적·제품·타깃 확정 | 현지조사 |
| D-21 | 인플루언서 협업 제안 | 인플루언서 |
| D-14 | 홍보 소재 초안 준비 | 마케팅 툴 |
| D-7 | 광고 문구·소재 최종 검토 | 마케팅 툴 |
| D-3 | 협업·채널 게시 일정 확정 | 인플루언서 |
| D-Day | 캠페인 공개·링크 확인 | 마케팅 툴 |
| D+3 | 초기 반응 확인 | KPI |
| D+7 | 캠페인 회고·개선점 기록 | KPI |

- 첫 진출 템플릿: 위의 **9개 업무**.
- 기념일 템플릿: D-35 현지조사를 제외한 **8개 업무**.
- 일수는 사용자가 바꿀 수 있는 계획 예시다. 한정선의 실제 표준 소요일이나 검증된 성과 공식이 아니다.
- 준비 기간은 주말을 포함한 달력일이다. 영업일·공휴일을 제외하는 자동 계산은 없다.

### 6.3 새 캠페인 만들기

1. 현지 기회의 **`+ 역산 캠페인 생성`**을 누른다.
2. 선택한 일정의 이름과 시작일이 캠페인명·목표일에 채워진다. 사용자가 바꿀 수 있다.
3. 첫 진출/기념일 템플릿을 고르고 제품·타깃·채널을 작성한다.
4. 업무명과 목표일 대비 일수를 조정한다. 음수는 목표일 전, 양수는 목표일 후다.
5. **일정 미리보기**로 계산 날짜와 이미 지난 마감을 확인한다. 미리보기만으로 저장하지 않는다.
6. **확정하고 캘린더에 반영**하면 캠페인·업무·달력·진척에 저장한다.

원하는 일정이 없으면 현지조사 탭에서 기념일·시즌을 먼저 등록하고 현지 기회의 조회 기간을 맞춘다. 복제는 기존 캠페인을 재사용하는 별도 기능으로 유지한다.

### 6.4 목표일 변경·복제·회고

| 기능 | 현재 동작 |
| --- | --- |
| 캠페인 선택 | 드롭다운으로 조회 대상을 고르고 상단 제목·D-n·타임라인·KPI를 바꿈 |
| 다음 할 일 | 선택 캠페인의 미완료 업무 중 우선순위 정렬상 첫 업무를 표시. 클릭하면 편집 폼 |
| 설정·재계획 | 목표일·업무명·간격을 바꾸고 미리보기 후 반영 |
| 보존 규칙 | 완료·취소·날짜 고정 업무는 기존 날짜·기록을 유지. 상대 날짜의 미완료 업무만 이동 |
| 중복 방지 | 같은 업무 ID를 갱신. 같은 미리보기를 반복 확정해 업무를 중복 생성하지 않음 |
| 복제 | 새 캠페인·업무 ID 생성, 취소 업무 제외, 완료 상태·협업 연결·회고 초기화 |
| 회고·관리 | 잘된 점·문제·다음에 바꿀 점을 텍스트로 기록하고 캠페인 상태 수동 변경 |

캠페인 상태는 준비·진행·완료·보류·취소·보관이다. 날짜가 지났다고 캠페인을 자동 완료 처리하지 않는다. HOME에서 목표일을 바꿔도 인플루언서 원본의 초안·게시일을 함께 바꾸지는 않는다.

### 6.5 간트 차트 읽기

- 각 행은 한 업무다. 가로축은 실제 날짜 간격을 사용한다.
- 바와 마감 지점, 마감일·상태, 한국 기준일의 점선을 표시한다.
- 완료는 옅은 색, 기한 초과는 붉은 계열로 구분한다. 업무명을 누르면 상세를 연다.
- 시작일이 있으면 **시작~마감**을 표시한다.
- 시작일이 없으면 **이전 마감부터의 준비 구간**을 사용하고 첫 업무는 마감 3일 전부터 표시한다. 바는 실측 작업 시간이나 자동 산정한 필요 인력이 아니다.
- 긴 차트는 카드 안에서 스크롤한다. 간격을 드래그해서 날짜를 바꾸는 기능은 없다.

## 7. 다른 탭에서 가져오는 핵심 신호

### 7.1 인플루언서 → 협업 요약

| 원본 항목 | HOME 활용 |
| --- | --- |
| 협업 ID·크리에이터명·캠페인 ID/이름·연결 기념일 | 카드 식별, 캠페인 연결, 같은 상세로 이동 |
| 진행 단계 | 제안 → 계약 → 초안 검토 → 게시 대기 → 완료 |
| 초안 제출일·검토 마감일·게시 예정일 | 달력 표시, 마감 경과·게시 임박 판단 |
| `requires_attention` | 담당자 확인 필요 배지 |
| `nextAction` | 다음 행동 한 줄 |

미완료 협업 중 **확인 필요**, **초안/검토 마감 경과**, **오늘부터 7일 이내 게시 예정**인 협업을 보여준다. 확인 필요 여부를 먼저, 그다음 게시일 순으로 정렬하며 HOME에는 최대 3건을 표시한다. 더 많은 기록은 원본 탭에서 확인한다.

마감 경과는 단계에 맞춰 판단한다. 제안·계약 단계는 초안 마감, 초안 검토 단계는 검토 마감을 확인한다. 게시 대기 단계에서 이미 끝난 초안 날짜만 보고 지연으로 판정하지 않는다.

**진척 시각화:** 연결된 원형 노드 5개에서 지난 단계는 체크, 현재 단계는 진한 올리브색과 테두리로 강조한다. ‘3/5단계 진행 중’처럼 표시하고 완료 상태는 5개를 모두 체크한다. 이는 단계 위치이며 업무량 기준 완료율·계약 확률이 아니다.

`협업 확인 ↗`은 해당 협업이 강조된 인플루언서 탭 상세로 이동한다. 원본에서 단계·마감을 수정하면 HOME이 다시 읽는다. 현재 캠페인 범위에서는 연결된 협업뿐 아니라 캠페인 미지정 협업도 요약에 포함한다. 달력의 현재 캠페인 협업 범위는 캠페인 ID/저장된 연결 ID를 기준으로 하므로 요약과 완전히 같은 대상은 아닐 수 있다.

> **팀 원본(진혁)과의 차이 — 연결 전 합의 필요**
>
> 위 표는 프로토타입의 협업 기록 기준이다. 진혁의 `influencer_marketing/public.py`는 이미 구현·시험이 끝났고 형식이 다르다.
>
> | 항목 | 프로토타입 (HOME) | 진혁 `get_collaborations()` |
> | --- | --- | --- |
> | 단계 | 5단계: 제안 → 계약 → 초안 검토 → 게시 대기 → 완료 | 8개 `status`: `candidate, sent, replied, negotiating, confirmed, shot, posted, declined` (+ `status_label`) |
> | 날짜 | 초안 제출일·검토 마감일·게시 예정일 | `available_shoot_dates`, `shoot_date`, `post_date` (초안·검토 날짜 없음) |
> | 캠페인 연결 | 캠페인 ID | `event_id`만 있음. 캠페인 연결은 HOME의 `home_campaign_collaboration_links`가 맡음 |
> | 확인 필요·다음 행동 | `requires_attention`, `nextAction` | 없음. HOME 요청 필드(`next_action`, `requires_attention`, `milestones`, `updated_at`)로 팀 README 8장에 등록됨 |
> | 이동 | `#workspace/creators/{creatorId}` | `link` 필드 · `/influencer_marketing/?collaboration_id=...` (편집 창 바로 열기는 합의 항목) |
>
> 진혁의 `get_today_tasks()`(`review`·`late`·`pick`·`soon`·`stale`)로 ‘확인 필요’를 대신하는 방법도 있다.
>
> **5개 노드 대응안 (진혁과 확정 전 제안):** ① 제안 = `candidate`·`sent`·`replied` ② 협상 = `negotiating` ③ 확정 = `confirmed` ④ 촬영 = `shot` ⑤ 게시 완료 = `posted`. `declined`는 HOME 요약에서 제외한다. 이 안을 채택하면 노드 이름이 ‘계약·초안 검토·게시 대기’에서 바뀌고, 마감 경과 판단도 초안/검토 마감 대신 촬영일·게시일 기준으로 바꾼다.
>
> **시간대:** 팀 README는 협업 일정을 베트남 시간(UTC+7) 기준으로 안내한다. HOME 달력에 한국 기준일과 함께 표시할 때 어느 시간대로 보일지 진혁과 정한다(날짜만 쓰면 대부분 같지만 자정 근처 시각이 생기면 달라진다).

### 7.2 현지조사 → 현지 기회

받는 항목: 일정 ID, 이름, 시작/종료일, 분류(공휴일/기념일/과일 시즌), 지역(다낭/베트남 전국), 출처명·URL.

- 제목은 **‘현지 기회’**다. ‘45일 내’라는 고정 제목은 제거했다.
- 기본 조회는 한국 기준일부터 앞으로 **45일**이다. 30·45·90일을 선택할 수 있다.
- 시작일·종료일을 달력에서 고르거나 직접 입력한 뒤 **조회**할 수 있다.
- 시작일과 종료일을 모두 포함해 **일정 시작일**이 범위 안에 있는 기록을 날짜순으로 보여준다. 이미 진행 중인 시즌은 시작일이 범위 밖이면 기회 목록에서는 제외되지만 달력에는 기간이 표시된다.
- 직접 과거 기간을 조회할 수 있다. D-n은 조회 시작일이 아니라 한국 업무 기준일과 비교하며 목표일이 지났으면 D+n으로 표시한다.
- 종료일이 시작일보다 앞서면 오류를 표시하고 저장하지 않는다.
- 선택한 기간은 데이터 모드별 브라우저에 저장한다. 프리셋은 현재 업무 기준일을 따라가며 직접 입력한 기간은 고정 날짜다.
- 각 항목의 `+ 역산 캠페인 생성`으로 캠페인 준비를 시작한다. 다른 연도의 기본 기념일도 해당 연도 날짜를 목표일로 전달한다.

기본 연례 일정은 **11월 20일 베트남 스승의 날**이다. 공휴일이 아닌 기념일로 분류하며 [기존 확인 출처](https://www.vietnam.vn/en/ngay-20-11-la-ngay-gi)를 표시한다. 전체 베트남 공식 공휴일·연휴가 자동 연동된 것은 아니다. 과일 시즌은 지역·기간·출처를 확인해 직접 등록해야 한다.

> **팀 원본(상준)과의 차이:** 팀 README의 `get_events(country="VN", year=None)`는 `event_id, country, name, date, type`만 돌려준다. 단일 `date`라서 과일 시즌의 시작~종료 기간, 지역(다낭/전국), 출처를 표시할 수 없다. HOME은 `start_date`·`end_date`·`region`·`source_name`·`source_url`·`is_demo` **필드 추가**를 요청한다(팀 README 8장 합의 항목). 합의 전에는 `date`를 시작일=종료일로 보고 하루 일정으로 표시한다. 일정 ID는 팀 규칙 `{국가코드}_{이름}_{연도}`(예: `vn_teachers_day_2026`)를 따른다.

### 7.3 현지조사 → 뉴스·트렌드

최신 등록 자료 최대 3건을 발행일 역순으로 읽는다. ‘최신’은 **자동 수집한 전체 기사 중 최신**이 아니라 **등록된 자료 중 최신**이다.

| 화면 부분 | 내용 |
| --- | --- |
| 사실 | 기사 제목, 지역·발행일·태그, 핵심 요약, 출처·원문 링크 |
| 적용 제안 | 한정선 캠페인·제품·포장·메시지에 어떻게 활용할지 한 줄 |
| 이동 | `콘텐츠 스튜디오로 ↗`를 누르면 제안 문구를 마케팅 툴의 브리프에 전달 |

예: 사실 요약 아래에 **‘적용 제안: 선물세트 포장과 구성품을 보여주는 카드뉴스를 준비합니다.’**를 분리해 보여준다. (프로토타입은 💡 이모지를 쓰지만, 팀 디자인 규격은 이모지 아이콘을 쓰지 않으므로 최종 버전은 선 아이콘이나 라벨로 바꾼다.) 제안은 원문이 입증한 사실이나 보장된 성과로 표시하지 않는다. 현재 제안과 요약은 수동 입력 또는 예시 자료이며 실제 AI가 작성하는 기능은 없다. 뉴스 자동 수집은 상준 담당이며 팀 README 9장 기준 Google 뉴스 RSS(베트남어)를 검토 중이다(NewsAPI는 베트남어 미지원).

> **팀 원본(상준)과의 차이:** 팀 README의 `get_news_summary(country="VN", limit=5)`는 `news_id, country, title, summary, source, published_at`을 돌려준다. HOME은 `limit=3`으로 부르고, **적용 제안(`suggestion`)·태그·지역·원문 URL** 필드 추가를 요청한다. 팀 원칙상 요약·가공은 원본 주인이 한 번만 하므로, 적용 제안도 상준 쪽에서 저장한 값을 읽어 표시만 한다. HOME이 다시 요약하거나 제안을 생성하지 않는다. 브리프 전달 대상은 최종 버전에서 `/content_studio/?tab=cardnews` 등 콘텐츠 스튜디오 URL이며, 전달 방식(쿼리 파라미터 등)은 유진·희주와 정한다.

### 7.4 KPI → 캠페인 한 줄 스냅샷

| 원본 항목 | HOME 표시 |
| --- | --- |
| 캠페인 ID | 현재 선택 캠페인의 기록만 연결 |
| 총 예산·집행액·통화·기록일·출처 | 예산 소진율 = 집행액/총 예산 |
| 핵심 지표 이름·값·단위 최대 2개 | 제품 페이지 방문, 구매 문의 등 입력한 지표 |
| 긍정·개선 VOC | 긍정/개선을 구분해 합계 최대 3개 키워드 |

표시 예: **예산 소진 65% · 제품 페이지 방문 1,280회 · 구매 문의 42건 · 긍정 #포장예쁨 #과일신선 · 개선 #가격부담 · KPI ↗**

이 수치는 예시 모드의 가상 성과다. 실측값으로 발표하지 않는다. 실제 업무에서는 KPI 탭에 입력한 기록을 사용한다. 예산 초과 시 100%를 넘는 소진율도 표시한다. 예산만으로 매출·전환율·ROAS를 추정하지 않는다.

- HOME의 큰 KPI 도넛 카드는 제거했고 디데이 업무 관리 카드 하단 한 줄로 통합했다.
- D+3·D+7 등 KPI 관련 업무의 마감일이 한국 기준일에 도달하면 업무에 해당 캠페인의 **KPI ↗**가 나타난다.
- 미래 업무의 KPI 연결은 미리 활성화하지 않는다. 캠페인 카드의 KPI 이동·성과 입력 링크는 사용할 수 있다.
- KPI를 확인한 뒤 HOME의 해당 캠페인 회고에 잘된 점·개선점을 기록한다. 회고 문장을 자동 생성하지는 않는다.

> **팀 최종 버전에서 확정되지 않은 연결 (중요)**
>
> - 팀 README 8장의 허용 연결 그림에는 **HOME → KPI 읽기가 없다.** KPI(`kpi/`)에는 `public.py`도 없다. 이 스냅샷을 최종 버전에 넣으려면 ① 팀이 연결을 채택하고 PM2가 연결 그림을 고친 뒤 ② 민지가 `kpi/public.py`에 캠페인 요약 함수를 공개해야 한다. 채택 전에는 최종 HOME에 스냅샷 대신 **KPI 탭 링크만** 둔다.
> - 민지의 KPI 설계는 광고비·매출을 채널 CSV(Meta·TikTok·Shopee)로 집계하고 예산을 KRW로 관리한다. **캠페인 ID 단위 집계가 가능한지** 확인해야 한다(현재 KPI 테이블 설계에 캠페인 ID 칸이 명시되지 않음).
> - 예산 소진율은 KPI 공식(팀 README 9장, 민지 제안: `(플랫폼 광고 집행비 + 인플루언서 협찬 집행비) ÷ 총 배정 예산 × 100`)이 확정되면 그 값을 받아 표시만 한다. HOME이 따로 계산하지 않는다.
> - VOC는 KPI 설계상 긍정/중립/부정 + 키워드 Top 5다. HOME의 ‘긍정/개선 합계 3개’ 표시를 어떻게 대응할지(예: 긍정 상위 2개 + 부정 상위 1개) 민지와 정한다.

### 7.5 시장점유율은 어디에 남아 있는가

초기 아이디어는 출처가 있는 미니 도넛으로 경쟁사 대비 점유율을 보여주는 것이었다. 최신 결정으로 **HOME의 점유율 차트·예시 45% 도넛·자료 준비 중 자리 모두 제거**했다.

현지조사 원본 탭의 수동 자료 입력·검증·도넛 표시는 남아 있다. 필요한 항목은 시장 정의·지역·기간·측정 기준·비교 항목·수치·출처다. 최소 2개 항목과 합계 100%를 검사한다. 검색·언급량 비중을 매출 시장점유율로 바꾸어 설명하지 않는다. 이 자료를 자동 수집하거나 한정선의 실제 점유율을 추정하는 기능은 없다.

> **팀 최종 버전:** 팀 README는 마켓셰어를 “데이터를 구할 수 없어 제외”로 정했다. 위 현지조사 탭의 점유율 입력·도넛은 **프로토타입에만 있는 기능**이며 상준의 현지 시장 분석 설계에는 없다. HOME은 최종 버전에서도 점유율을 표시하지 않는다(팀 README의 ‘HOME은 자료 준비 중 표시’ 문구는 **전체 제거**로 바꾸도록 PM2에게 요청).

## 10. 랜딩페이지·브랜드 이미지·모션

### 10.1 디자인 기준과 현재 구성

디자인 출발점은 [한정선 공식 사이트](https://hanjungsun.co.kr/HOME)와 업로드한 브랜드·제품 사진이다. 큰 사진·크림색 여백·세로 조판·차분한 모션은 [가마쿠라 레퍼런스](https://www.warabimochi-kamakura.com/)를 참고했다. 원본 사이트를 픽셀 단위로 복제하거나 일본 브랜드의 사진·연혁을 가져온 것은 아니다.

현재 구성은 큰 사진 슬라이드 → 10장 브랜드 사진 연출 → 제품/선물세트 → 구매 안내 → 베트남/다낭 지도 → 세계지도 → 푸터다. 한국어의 일부 전시 문구는 세로 조판을 사용하며 영어·베트남어는 읽기 쉬운 가로 조판을 유지한다.

### 10.2 사진과 콘셉트 구분

- 랜딩의 매장·제품·패키지 사진은 업로드한 **`제목 없는 디자인.zip`**의 고화질 브랜드 자료에서 교체했다.
- 추출한 사진 13개의 원본 페이지·크롭 범위는 `dist/assets/collection/sources.json`에 기록한다. 확대 보간이나 생성형 보정 없이 WebP로 제공한다.
- 한국 매장 사진을 다낭의 실제 매장으로 설명하지 않는다.
- 이전 AI 패키지/신메뉴 콘셉트 보드는 현재 랜딩의 판매 사진으로 노출하지 않는다. 소스에 남아 있는 콘셉트 파일도 실제 출시 SKU나 확정 매장 자료가 아니다.
- 마케팅 툴의 용과요거트·두리안 제품은 현지화 메뉴 **콘셉트**다. 판매 확정 제품으로 간주하지 않는다.

### 10.3 사진 모션

- 첫 화면은 사진 3장의 느린 확대·페이드 슬라이드다. 수동 선택과 일시정지가 있다.
- 이후 약 10장의 브랜드 사진이 서로 다른 크기·회전·위치로 펼쳐지고 아래로 떨어진다. 스크롤을 되돌리면 장면도 되돌아간다.
- 페이지 스크롤을 강제로 가로채지 않는다. 사진 장면은 sticky 구간과 스크롤 위치를 사용한다.
- 슬라이드는 화면 밖·탭 숨김 시 정지한다. 모션 줄이기 설정에서는 사진을 정적인 격자로 제공한다.

### 10.4 베트남 → 다낭 지도 확대

- 왼쪽: 베트남 전체 윤곽에 **하노이·다낭·호치민** 표시.
- 오른쪽: 실제 고도 자료를 기반으로 **선짜 반도·한강·미케 비치·다낭만**을 읽을 수 있는 지형선 지도.
- 다낭 위치에서 오른쪽으로 투사선·면이 이어지고 지역 지도가 확대되는 모션을 제공한다. 아주 좁은 화면에서는 두 지도가 세로로 쌓이고 연결선은 숨긴다.
- 모션 줄이기 설정에서는 최종 지도를 정적으로 표시한다.
- 베트남·세계 윤곽은 Natural Earth, 다낭 고도는 Mapzen Terrain Tiles, 한강 선은 OpenStreetMap 자료를 사용한다. 화면에 출처를 표시한다.
- 해안은 고도 기반 근사 표현이며 행정구역·지적 경계·항해용 지도가 아니다.

지도 아래의 세계지도는 **글로벌 확장을 검토 중이라는 방향**을 표현한다. 확정된 해외 매장이나 진출 국가를 임의로 추가하지 않는다. 푸터는 배경색을 통일하고 왼쪽 고정 로고와 겹치는 로고는 제거했다.

자료·처리 방식 상세는 `ASSETS-LANDING.md`와 [Mapzen 자료](https://registry.opendata.aws/terrain-tiles/), [OpenStreetMap 저작권 안내](https://www.openstreetmap.org/copyright), [Natural Earth 이용 안내](https://www.naturalearthdata.com/about/terms-of-use/)를 따른다.

### 10.5 구매 안내의 한계

제품을 문의 목록에 담고 수량을 수정한 뒤 문의 문구를 복사할 수 있다. 실제 결제, 주문 접수, 확정된 다낭 가격·재고·매장·개점일·수신 채널은 연결하지 않았다. 직원용 대시보드 진입 링크는 상단·지도·푸터에 둔다. 팀 범위상 회원가입·결제·주문·물류는 제외이므로 문의 목록 이상으로 확장하지 않는다.

### 10.6 팀 최종 버전에서 정할 것

- **담당·위치:** 팀 README 5장 폴더 구조에는 랜딩(첫 접속 화면)이 들어갈 자리가 없고, 7장·6.8에서 “첫 접속 화면 경로와 담당은 PM1·PM2가 확정”으로 남아 있다. 이 장의 랜딩은 HOME 프로토타입에 붙여 만든 시안이며, `home/` 폴더 소유로 확정된 것이 아니다.
- **사진 사용 허락:** 팀 README 6.8은 공식 홈페이지 이미지 사용 허락 또는 자체 촬영을 확정 항목으로 둔다. `제목 없는 디자인.zip`의 브랜드 사진도 사용 범위를 확인한 뒤 최종 버전에 넣는다. 대용량 원본 이미지는 Git이 아니라 팀 공유 드라이브에 둔다.
- **디자인:** 팀 기준 시안은 희주의 `docs/design/hanjungsun-vietnam-dashboard.html`이다. 랜딩도 6장 색·글꼴 변수에 맞춘다.

## 11. 데이터 모드·시간·저장 규칙

### 11.1 예시와 실제 업무의 분리

- **예시 보기:** 가상 캠페인, 협업 A/B/C, 일정, 뉴스 형식, 점유율, 성과를 별도 저장소에서 다룬다. 예시를 수정해도 실제 업무 기록을 바꾸지 않는다.
- **내 업무:** 사용자가 입력한 기록을 사용한다. 없는 성과·뉴스·협업을 가상 값으로 채우지 않는다. 기본 연례 기념일은 제공한다.
- 기존 실제 캠페인/업무·협업·조사 기록이 있으면 실제 보기로 시작하고, 없으면 예시 보기를 먼저 제시한다. 사용자가 선택한 데이터 모드는 유지한다.
- 예시의 망고 시즌 기간은 실제 제철 정보가 아니며 예시라고 표시한다. 예시 점유율·KPI·뉴스도 실측 사실로 발표하지 않는다.
- 예시 날짜는 최초 생성 당시를 기준으로 만든다. 저장된 목표일이 매일 자동으로 뒤로 밀리는 것은 아니다.

### 11.2 날짜와 마감

한국의 오늘을 기본 업무 기준일로 사용하고 날짜 버튼에서 지정 기준일로 바꿀 수 있다. 지정 기준일을 쓰면 D-n·오늘·지연 판단도 그 날짜를 기준으로 한다. 베트남 시계는 실제 현지 시각을 표시한다.

업무에는 현재 **날짜만** 입력하며 시간 단위 마감은 없다. 당일 마감 업무를 그날이 끝나기 전에 지연으로 처리하지 않는다. 날짜만 있는 역산은 UTC 기반 날짜 연산을 사용해 월말·연말·윤년을 처리하고, 한국 기준일 판정과 분리한다.

### 11.3 저장 위치와 연결의 실제 범위

### 11.4 기존 기록 처리

과거 `hjs-campaign`, `hjs-tasks`는 HOME 첫 진입 시 새 모델로 한 번 가져오며 원래 키는 삭제하지 않는다. 과거 SCM 템플릿은 마케팅 템플릿으로 전환하고 `supply`로 분류된 업무·기존 OEM 샘플 기본 업무는 별도 보관 배열에 둔다.

기존 마케팅 완료·고정 날짜·직접 입력 기록은 보존한다. 모든 사용자 문장에서 물류 의미를 AI가 판정해 삭제하는 기능은 아니다. 과거 계산 코드가 남아 있어도 현재 HOME에서 SCM 템플릿을 제공하지 않는다.

## 13. 최종 팀 개발용 인터페이스·모델 제안

**현재 사이트에 서버 API나 DB가 존재한다는 뜻이 아니다.** 아래는 팀 전체 README에서 이미 정해진 것과, HOME이 추가로 요청할 것을 구분한 표다.

### 13.1 HOME이 읽는 공개 함수

| 원본 | 팀 README에 정해진 형식 | HOME 추가 요청 (합의 전) |
| --- | --- | --- |
| 상준 `market_analysis/public.py` | `get_events(country="VN", year=None)` → `event_id, country, name, date, type(holiday·anniversary·fruit_season)` | `start_date`, `end_date`, `region`, `source_name`, `source_url`, `is_demo` |
| 상준 `market_analysis/public.py` | `get_news_summary(country="VN", limit=5)` → `news_id, country, title, summary, source, published_at` | `suggestion`(적용 제안), `tags`, `region`, `url` |
| 진혁 `influencer_marketing/public.py` (구현 완료) | `get_collaborations(event_id=None, include_demo=True)` → `collaboration_id, event_id, influencer, main_platform, followers, status, status_label, available_shoot_dates, shoot_date, post_date, is_demo, link` | `updated_at`, `milestones`, `next_action`, `requires_attention` (팀 README 8장에 이미 등록) |
| 진혁 `influencer_marketing/public.py` (구현 완료) | `get_today_tasks(limit=10, include_demo=True)` → `task_id, kind, collaboration_id, influencer, title, detail, due_date, is_demo, link` | 없음. ‘확인 필요’ 판단에 활용 검토 |
| 민지 `kpi/` | **없음 — HOME → KPI는 허용 연결이 아님** | 채택 시 `get_campaign_kpi_summary(campaign_id)` → 캠페인 ID, 총 예산, 집행액, 통화, 지표 최대 2개, VOC, 기준일·출처 |

- 마켓셰어는 팀 결정으로 제외했으므로 `get_market_share_summary`는 만들지 않는다.
- 진혁 함수는 오류 시 `[]`, 값 없음 시 `""`/`None`을 돌려준다. HOME은 `try/except`로 감싸 원본 실패 시에도 화면이 멈추지 않게 하고, “삭제됨”(정상 조회했는데 ID 없음)과 “정보를 불러오지 못함”(조회 실패)을 구분해 표시한다.
- 시연 데이터는 원본의 `is_demo`/`include_demo`로 구분한다. 프로토타입의 ‘예시 보기 / 내 업무’ 전환은 최종 버전에서 `include_demo` 값과 `DEMO · 예시 데이터` 배지로 대응한다.
- 현재 프로토타입 JavaScript 필드는 `campaignId`, `targetDate`, `draftDate`, `reviewDate`, `postDate`, `requires_attention`, `nextAction`처럼 작성되어 있다. 최종 버전은 원본 함수의 snake_case 필드를 그대로 쓰고, 이름이 다른 필드(예: `draftDate`→없음, `postDate`→`post_date`)는 7.1의 대응안을 따른다. 함수명만 맞춘다고 연결되는 것은 아니다.

팀 README 5장에 `home/models.py`의 테이블 4개가 등록되어 있다. 아래는 각 테이블의 필드 제안이다.

| 모델 | 주요 필드 |
| --- | --- |
| `home_campaigns` | ID, 이름, 목표일, 템플릿, 상태, 제품, 타깃/채널, 원본 일정 ID, 회고 |
| `home_tasks` | ID, 캠페인 ID, 템플릿 업무 키, 업무명, 시작/마감일, 상대 일수, 고정/상대 방식, 상태, 중요도, 관련 탭, 메모, 완료 시각 |
| `home_schedules` | ID, 일정명, 날짜, 캠페인 ID, 메모. 기존 직접 일정 호환용 |
| `home_campaign_collaboration_links` | 캠페인 ID, 협업 ID(`collaboration_id`). 진혁 원본에는 캠페인 ID가 없으므로 캠페인–협업 연결은 HOME이 이 테이블로 관리한다 |

- 다른 탭 ID(`event_id`, `collaboration_id`, `news_id`)는 DB 외래키 없이 **문자열 칸**으로 저장한다. 원본 내용(이름·날짜·단계)을 HOME 테이블에 복사해 관리하지 않는다. 단 캠페인명·목표일은 캠페인 생성 시 사용자가 정하는 HOME 소유 값이며, 원본 일정 ID를 함께 저장한다.
- ID는 팀 규칙대로 **문자열**을 쓴다(형식 `{국가코드}_{이름}_{연도}`, 주인만 생성, 생성 후 변경 금지). 프로토타입의 구형 숫자 협업 ID는 이관 시 문자열로 바꾼다.
- 날짜는 `YYYY-MM-DD`, 완료 등 시각은 UTC 저장·한국 기준 표시를 제안한다(시간대 저장 방식은 PM1과 확정). 원본 삭제, 누락, API 실패, 실제 0건을 구분하고 없는 값을 0이나 더미 성과로 바꾸지 않는다. 취소 업무의 완료율 제외·고정 업무 보존 규칙을 서버에서도 유지한다.

## 부록 B. 브리핑·시연 순서

### 1분 설명

“HOME은 한정선의 다낭 마케터가 오늘 해야 할 일과 캠페인 준비 상태를 확인하는 시작 화면입니다. 위쪽에는 달력과 업무 진척, 중간에는 디데이 업무와 현지 기회·협업, 아래에는 뉴스 적용 제안이 있습니다. 기념일을 고르면 준비 업무가 목표일에서 거꾸로 배치되고, 체크 한 번으로 달력·완료율·간트가 함께 바뀝니다. 협업과 KPI는 전체 분석 대신 확인할 핵심만 보여주며 상세는 담당 탭으로 이동합니다. 현재는 브라우저에서 작동하는 프로토타입이고 실제 AI·SNS·GA 연결은 다음 단계입니다.”

### 기능 시연

1. 랜딩에서 고화질 브랜드 사진·사진 모션·베트남→다낭 확대 지도를 확인한다.
2. ‘대시보드 바로가기’를 누르고 헤더 토글로 미니 메뉴를 확인한다.
3. ‘예시 보기’에서 캠페인 D-n, 달력, 완료율을 본다. 최초 예시의 전체 업무는 13건, 완료 2건으로 15%이며 이후 편집에 따라 바뀐다.
4. 지연·보류·일정겹침 필터를 눌러 목록이 바뀌는 것을 보여준다.
5. 미완료 업무 하나를 체크하고 완료율·달력·간트의 동시 변화를 확인한다. 완료 보기에서 되돌릴 수 있다.
6. 현지 기회의 기간을 바꾸고 직접 날짜를 조회한다. 한 일정을 선택해 새 캠페인 미리보기까지 보여준다. 저장을 원하지 않으면 확정하지 않는다.

- **숙지·브리핑 보완:** USAGE 12절에 HOME/보고서 목적, 공공부문 표시, 실제 기록 관리 동작, 진혁과 합의할 협업 항목, 1분 브리핑 초안을 정리했다. 오래된 가져오기 ‘통째 교체’ 안내는 내 업무(안전한 추가)와 DEMO(교체)로 구분해 바로잡았다.
- 보고서는 ‘이벤트 실행계획·진행현황서’로 목적을 명시하고 업무 시작·마감·메모, 현지 일정 적용 범위, 미정·보류 건수, 회고를 표시한다. 기존에 빠져 있던 같은 이벤트의 HomeSchedule을 읽어 포함한다. 관리 기간은 해당 업무·직접 일정·연결 협업의 유효 날짜와 목표일을 포함하며 다른 이벤트 일정과 취소 업무는 제외한다. 자체 콘텐츠 준비 업무 마감일을 실제 콘텐츠 전체 게시 일정으로 설명하지 않는다. DB/API 구조는 바꾸지 않았다.
- 조회 기간 상자와 업무 편집 dialog에도 가로·세로 resize를 추가했다. 입력 필드·버튼 자체는 일반 입력 요소로 유지한다. dialog는 기존 기본 너비와 화면 높이 상한을 유지한다.
- 보고서는 서버 이벤트를 읽으므로 DEMO 링크를 눌렀을 때 404로 이동하지 않고 내 업무에서 사용할 수 있다는 안내를 표시한다.
- 확인: 메모리 DB에서 기존 회귀 16개와 보고서 구성·직접 일정·이벤트 격리·기간·미정/보류·오류 처리·메모 안전 표시 13개 통과. 보고서 버튼의 내 업무/DEMO 동작 7개 통과. 실제 DB·JSON 파일의 전후 해시가 같고 HOME 및 번역 활성 상태를 확인했다. 인쇄 결과의 시각 점검과 새 손잡이의 실제 드래그 확인은 남아 있다.

- **추가 피드백 반영:** 주요 카드·검색 결과·등록 공지 카드에 브라우저 기본 `resize: both`를 적용했다. 가로는 해당 열 너비 안에서, 세로는 스크롤 가능한 범위에서 조절한다. 하단 초기화 버튼은 화면 크기만 지우며 기록 API를 호출하지 않는다. 서버 DB·브라우저 업무 원본에는 크기를 저장하지 않는다.
- 오른쪽은 하나의 컨테이너에서 `repeat(3, minmax(240px, 1fr))`로 기본 3등분한다. 왼쪽 전체 높이를 기준으로 공간을 나누고, 오른쪽 카드를 조절하면 해당 높이를 행에 반영해 겹치지 않게 한다. 최소 높이 때문에 공간이 부족하면 컨테이너를 스크롤한다. 작은 화면은 세로 배치·동일 기본 높이를 사용한다.
- 뉴스의 버튼·검색창·검색 결과·규제 공지 바깥선과 공지 카드 테두리를 제거했다. 검색창은 옅은 면, 등록 공지는 베이지·청록·살구 계열의 세 면으로 구분한다. 제안과 원문·교차 근거는 유지하며 키보드 포커스 표시는 남긴다. 캘린더 면은 공통 흰색 토큰으로 강조한다.
- KPI 탭은 읽기만 참고했다. 공통 `--teal`·`--beige`·`--celadon`·`--orange`를 섞어 완료·확인 필요 업무 등 강조에 사용한다. KPI 전용 분홍·빨강 값을 HOME에 복사하거나 공통 CSS를 바꾸지 않는다. 달력 범주 색과 하루 4개·고정 행 높이는 유지한다.
- 협업 요약은 공개 함수가 제공하는 이름·대표 채널·상태·촬영일·게시일과 공개 할 일의 `detail/title`을 표시한다. 예시 모드에만 가상 크리에이터 3명과 다음 행동을 구성했다. 실제 모드에 더미를 섞거나 다른 탭 테이블을 직접 조회하지 않는다. 인플루언서 탭 자체는 수정하지 않았다.
- 같은 뉴스가 다시 렌더링될 때는 DOM을 교체하지 않아 조절한 공지 크기와 펼침 상태를 보존한다. 원본 목록이 새로 로딩되거나 바뀌면 새 카드로 표시한다.
- 추가 확인: 크기 변경의 행 반영·초기화·기본 3등분·색상/고정 행 보존·뉴스 펼침 상태 보존·협업 내용/DEMO/실패 분리 등 46개 화면 코드 검사와 메모리 DB의 기존 회귀 시험 16개 통과. 실제 DB·JSON 파일의 전후 해시가 같고 실행 중인 HOME/JS 제공 및 번역 활성 상태를 확인했다. 브라우저에서 실제 손잡이를 드래그하는 조작·크기별 배치의 시각 확인은 남아 있다.

- **1차 피드백 반영:** 검색 결과와 규제·공지 영역을 공통 흰 바탕 토큰(`--page-bg`)으로 바꾸고, 공지 세 건을 개별 배경·테두리 카드로 구분했다. 바깥쪽 굵은 왼쪽 선은 제거했다.

- 진척·오늘 할 일을 구분선이 있는 하나의 카드로 합쳤다. 큰 화면은 캘린더/업무·현지 기회와 뉴스/협업을 같은 그리드 행에 배치한다. 오른쪽 내용이 많으면 해당 목록을 스크롤한다. 작은 화면은 기존 세로 흐름으로 돌아간다.
- 등록 뉴스의 펼침 영역에 `sources`의 원문·교차 출처·뒷받침 내용과 `verification_notes`를 표시한다. 서버/API·데이터 구조 변경 없이 기존 응답을 사용한다.

- 번역 구현 점검 메모: 현재 `translate.py`의 요청은 `source_lang=VI`를 고정한다. VnExpress 영문 제목의 번역 품질은 별도 확인이 필요하다. 이번 UI 작업에서는 번역 로직을 바꾸지 않는다.
- 이번 확인: 화면 ID 보존·상자 병합·그리드 배치·공통 토큰·뉴스 출처 표시·안전한 링크 등 120개 구조/표시 검사와 기존 기능 회귀 시험 16개 통과. 회귀 시험은 메모리 DB에서 실행했다. 실행 중인 HOME은 HTTP 200, 번역 설정은 활성 상태다. 실제 브라우저 시각 점검은 URL을 확인하지 못한 컴퓨터 도구의 정책 제한으로 중단했으며, 화면 너비별 줄바꿈·배치 균형은 확인이 남아 있다.

- 화면 전환을 책갈피 탭으로 정리하고, 상단 데이터·표시 범위·기록 관리를 같은 높이의 선택 상자로 맞췄다.
- 기록 관리 선택은 기존 내보내기·가져오기·이관 처리에 연결한다. 기존 확인 절차와 저장 방식은 유지한다.
- 오른쪽 카드의 제목·여백·버튼 높이를 통일했다. 조회 기간의 직접 날짜 입력은 펼쳐서 사용한다.
- 주 보기의 시간 칸 간격과 종일 일정 표시를 정리했다. 일정이 많으면 종일 영역에서 스크롤한다. 월 보기의 하루 4개 제한·고정 행 높이·범주 색은 유지한다.
- 확인: 헤더·탭 동작 16개, 조회 기간·화면 구조 14개, 제공된 기존 회귀 시험 16개 통과. 회귀 시험은 메모리 DB에서 실행해 실제 기록을 변경하지 않았다.
- 남은 확인: 실제 브라우저에서 화면 너비별 줄바꿈·주 보기·기록 관리 3개 동작을 눈으로 확인한다. 이번 실행에서는 컴퓨터 도구가 현재 브라우저 URL을 확인하지 못해 실제 화면 점검을 중단했다.

### 이벤트 실행 계획서 (2026-10-26)

선택한 이벤트의 실행 계획서를 `/home/report/<이벤트 ID>`에서 인쇄·PDF로 뽑는다.

- 서버에서 PDF 파일을 만들지 않는다. PDF 라이브러리가 없고 `requirements.txt`는 PM1 전용이다.
  브라우저 인쇄(Ctrl+P → PDF로 저장)를 쓰며, 결과물은 같고 한글도 깨지지 않는다.
  1클릭 내려받기가 필요해지면 그때 PM1에게 라이브러리를 요청한다.
- 담는 것: 개요, 준비 기간의 현지 일정, 진행 현황, 업무 일정,
  콘텐츠·협업 업로드 일정, 남은 일.
- **KPI 수치는 담지 않는다.** `kpi/public.py`가 없고, "KPI는 일반 탭 링크만 제공한다"는
  팀 합의(연동 보류)가 있으며, 소비자 반응 분석은 KPI 탭의 산출물이다.
  두 탭이 같은 숫자를 각각 만들면 어긋났을 때 어느 쪽이 맞는지 알 수 없다. 링크만 둔다.
- **콘텐츠의 내용·형식·문구도 담지 않는다.** `content_studio/public.py`가 없어 읽을 수 없고,
  내용 기획은 콘텐츠 스튜디오 담당이다. 보고서에는 일정만 담는다.
  내용까지 담으려면 유진·희주에게 공개 함수를 요청해야 한다.
- 인플루언서 협업은 `influencer_marketing/public.py`로만 읽고, 실패해도 나머지 항목은 그대로 낸다.

### 기능 동결 (2026-10-26)

아래 세 가지가 되면 HOME은 완성으로 본다. 2026-10-26 기준 셋 다 동작한다.

1. 이벤트를 만들면 준비 업무가 날짜까지 자동으로 깔린다.
2. 오늘 할 일과 베트남 현지 일정을 한 화면에서 본다.
3. 이벤트 상황을 문서 한 장으로 뽑아 팀에 공유한다.

**새 기능과 새 외부 API를 추가하지 않는다.** 날씨·환율·트렌드 차트 같은 위젯은 넣지 않는다.
이 탭의 역할은 일정 역산과 오늘 할 일이며, 성과는 KPI, 소재는 콘텐츠 스튜디오,
시장 조사는 현지 시장 분석이 원본이다. 경계를 넘지 않는 것이 이 탭의 신뢰도다.

외부 의존은 세 개(Calendarific·구글 뉴스 RSS·DeepL)로 고정한다. 셋 다 실패해도 화면이
멈추지 않도록 처리해 두었다. 네 번째를 붙이면 고장 지점이 늘고 점검할 것이 늘어난다.
필요가 실제로 생기면 그때 검토한다.

다음에 기능을 더할 때는 **상상이 아니라 실사용에서 나온 불편**을 근거로 한다.
2주 정도 실제로 써 본 뒤 나온 목록만 구현한다.

**보류 후보(event_candidates.json)는 화면에 올리지 않는다.** 검증되지 않은 자료를
화면에 두면 검증한 자료와 섞여 읽히고, 그 순간 달력 전체의 신뢰도가 떨어진다.
기록으로만 남기고 근거가 갖춰지면 정식 등록 절차로 올린다.

  저장하는 기능을 만들었다. 사용자 승인 후 실제 기록 29건의 이관과 원본 보존·재검사까지 완료했다.
- **4단계: 화면의 서버 저장 연결 완료.** 여러 기록의 동시 저장·확인한 이벤트 삭제·다른 창과의 충돌 방지를
  구현했다. 실제 29건은 시험용으로 수정·삭제하지 않았다. 상세 동작과 검사 결과는 아래 4단계 절을 참고한다.
- 다음은 업무 범주 직접 지정과 필요한 다른 탭 연결 확인 등 남은 기능·데이터·API 작업이다.
  PM1에게 DB 반영 결과를 공유할 요청문은 아래에 있으며, 아직 전달하지 않았다.
  각 단계에서 변경 파일과 방법을 먼저 보고한다. UI 다듬기는 기능·데이터·API 작업 이후에 한다.
- 실제 테이블은 사용자 승인으로 `flask --app app init-db`를 실행해 반영했다.
  HOME 4개와 다른 탭의 누락 테이블 4개가 생성됐다. 기존 DB를 지우지 않았고 기존 테이블·인덱스 정의 유지와
  소스 파일/Git 작업 상태 불변을 확인했다. PM1 즉답이 어려워 기다리지 않고 진행하라는 사용자 지시에 따른 실행이다.

#### 1단계에서 정의한 저장 항목

| 테이블 | 저장 항목 |

| `home_campaigns` | `id`, `name`, `target_date`, `template`, `status`, `product`, `audience`, `channel`, `event_id`, `review` |

- 모든 테이블에 `revision`(수정 번호)과 `import_batch_id`(어느 이관 작업에서 추가됐는지)를 둔다.
  수정 번호는 SQLAlchemy의 일반 객체 수정·삭제 시 오래된 기록으로 덮어쓰는 것을 감지한다.
  이후 API에서도 클라이언트가 읽었던 번호를 검사해야 한다. 일괄 SQL 수정은 이 보호를 우회하므로 사용하지 않는다.
- 기존 문자열 ID를 유지한다. `event_id`와 `collaboration_id`에는 외래키가 없다.
  HOME 내부의 `campaign_id`만 HOME 캠페인과 연결하며, 자동 연쇄 삭제는 설정하지 않았다.
- 날짜는 DB의 날짜 형식으로 저장한다. 브라우저에서 비어 있던 업무 날짜는 `NULL`로 대응한다.
  `due_time`은 기존 KST 기준 `HH:MM` 문자열, `completed_at`은 기존 UTC ISO 문자열을 보존한다.
  완료 시각 미기록은 빈 문자열을 유지한다. 팀 전체 시간대 형식 합의를 대신 정하지 않는다.
- 업무 상태·중요도와 시작일/마감일 순서에 DB 검사를 둔다. 잘못된 기존 기록은 이후 이관 단계에서
  사용자에게 알리고 중단하며, 날짜나 상태를 임의로 바꾸지 않는다.
- `home/__init__.py`가 이미 모델을 불러오므로 공용 앱 수정은 필요 없다.
  1단계에는 새 라이브러리·환경변수·API·화면 변경이 없다.

#### 2단계: 서버 저장·조회 사용 방법

화면은 아래 4단계의 묶음 저장 API를 사용하며, 2단계의 개별 API도 유지한다.
기존 브라우저 기록을 자동으로 옮기거나 DB를 자동 생성하지 않는다.
2단계 API는 실제 HOME 업무 전용이다. 예시 모드와 화면 설정(`preferences`)은 브라우저에 유지하며,
백업 파일 이관은 아래 3단계 전용 API를 사용한다.
기존 `/home/api/signals`와 뉴스 API는 그대로 유지한다.

| 요청 | 주소 | 하는 일 |
| --- | --- | --- |
| `GET` | `/home/api/work/campaigns` | 이벤트 목록 조회 |
| `POST` | `/home/api/work/campaigns` | 이벤트 한 건 추가 |
| `PATCH` | `/home/api/work/campaigns/<id>` | 이벤트 한 건 수정 |
| `GET` / `POST` | `/home/api/work/tasks` | 업무 목록 조회 / 한 건 추가 |
| `PATCH` | `/home/api/work/tasks/<id>` | 업무 한 건 수정 |
| `GET` / `POST` | `/home/api/work/schedules` | 직접 일정 목록 조회 / 한 건 추가 |
| `PATCH` | `/home/api/work/schedules/<id>` | 직접 일정 한 건 수정 |
| `GET` / `POST` | `/home/api/work/links` | 캠페인–협업 연결 목록 조회 / 한 건 추가 |

- 업무·일정·협업 연결 목록은 `?campaign_id=<이벤트 ID>`로 좁혀 볼 수 있다.
- 목록 응답은 `{"items": [...]}`, 추가·수정 응답은 `{"item": {...}}`다.
  각 기록에 `revision`(수정 번호)을 함께 반환한다. 이관 묶음 ID는 일반 응답에서 제외한다.
- 추가는 기존 필드 이름으로 JSON 한 건을 보낸다. 예를 들어 이벤트는
  `{"id":"vn_home_example_2026","name":"시험용 이벤트","target_date":"2026-11-20"}`다.
  이 예시는 사용 설명용이며 실제 자료에 저장하지 않았다.
- 수정은 바꿀 필드와 마지막으로 읽은 `revision`을 보낸다.
  예: `{"revision":1,"status":"doing"}`. 수정 번호가 오래됐으면 저장하지 않고 새로고침을 안내한다.
- ID와 이관 묶음 ID는 수정할 수 없다. 협업 연결은 두 ID 자체가 연결의 기준이므로 수정 API가 없다.
  2단계에는 삭제·여러 기록의 동시 저장을 넣지 않았으며, 4단계에서 별도 승인 후 묶음 저장 API로 구현했다.
- 업무의 비어 있는 시작일·마감일은 입력에서 `""` 또는 `null`을 받고, 응답은 `null`로 보낸다.
  시간이 없으면 `due_time`과 `completed_at`은 빈 문자열이다. 완료 시각을 임의로 생성하지 않는다.
  일정에 캠페인이 없으면 `campaign_id`를 생략하거나 `null`로 보낸다.
- 날짜·시간·상태·관련 탭과 HOME 캠페인 연결을 검사한다. 모르는 필드나 잘못된 자료는 거부하며
  조용히 버리거나 다른 값으로 바꾸지 않는다. 외부 협업의 존재 여부는 이 저장 API에서 조회하지 않는다.
- 저장 요청은 JSON 객체, 최대 128 KiB이며 크기를 확인할 수 없는 요청도 거부한다.
  다른 사이트에서 보낸 저장 요청을 거부한다. 사용자별 로그인·접근 권한 기능을 새로 추가한 것은 아니다.
- 오류는 `{"error":"설명"}`으로 알린다. 입력 오류 `400`, 다른 사이트 요청 `403`, 없는 기록 `404`,
  지원하지 않는 수정 `405`, 중복·수정 충돌 `409`, 요청 크기 초과 `413`, JSON 외 형식 `415`,
  DB 미준비·연결/저장 오류 `503`이다. DB 실패를 정상 빈 목록으로 바꾸지 않으며 SQL·원본 예외를 노출하지 않는다.
- 추가·수정 한 건은 성공 시에만 확정한다. 실패하면 해당 요청의 변경을 취소한다.
  응답에는 `Cache-Control: no-store`를 붙인다. API에서 `create_all()`이나 실제 DB 초기화를 실행하지 않는다.
- 확인: `.venv/Scripts/python.exe -B -`로 임시 검사 코드를 실행해 **68개 API 검사 통과**.
  저장·조회·수정, 중복·오래된 수정 번호 차단, 잘못된 날짜·시간·연결 거부, DB 미준비와 저장 실패 시
  취소·오류 안내를 확인했다. 합성 자료와 메모리 DB만 사용했고 `.env`·실제 DB·외부 API는 사용하지 않았다.

#### 3단계: 백업 파일에서 서버로 옮기기 (실제 이관 완료)

**2026-10-25 실제 이관 완료:** 사용자가 지정한 내 업무 백업에서 이벤트 3개·업무 26개를 저장했다.
일정·협업 연결은 0건이다. 저장 직전 검사에서 신규 29건·중복 0건·충돌 0건을 확인했고,
저장 후 같은 백업을 다시 검사해 동일 29건·신규 0건·충돌 0건을 확인했다.
브라우저 저장소는 조작하지 않았고, 원본 파일의 해시가 이관 전후 같은지도 확인했다.

- 원본 백업: `C:\Users\user\Downloads\home-backup-work-2026-10-25.json`
- 이관 결과: `C:\Users\user\Downloads\home-migration-result-2026-10-25.json` (새 파일로 저장하고 다시 읽어 검증)
- 원본·결과 파일의 기록 내용은 저장소에 복사하거나 출력하지 않았다. 예시 백업은 이관하지 않았다.
- DB 명령에는 `FLASK_SKIP_DOTENV=1`, `PYTHONDONTWRITEBYTECODE=1`을 적용했고 `.env`를 읽지 않았다.

아래는 이후 추가 백업을 옮길 때 사용하는 방법이다. 추가 이관도 검사 결과를 보고하고 별도로 승인받는다.

1. 데이터 선택을 ‘내 업무’로 바꾸고 기존 ‘내보내기’로 백업 파일을 받는다.
2. ‘서버로 옮기기’ → ‘백업 파일 선택’에서 그 파일을 선택한다.
3. 이벤트·업무·직접 일정·협업 연결별로 **새 기록·같은 기록·충돌** 건수를 확인한다.
   파일을 고르거나 검사하는 것만으로 서버에 저장하지 않는다.
4. 충돌이 없고 새 기록이 있을 때만 ‘확인한 새 기록 옮기기’를 누를 수 있다.
   같은 기록은 건너뛰며, 하나라도 내용이 다르면 전체 이관을 막는다.
5. 완료 창에서 ‘옮긴 결과 파일 받기’를 눌러 원래 백업 파일과 함께 보관한다.
   실제 다운로드 완료 여부는 브라우저 다운로드 목록에서 직접 확인한다.
   결과 파일을 받기 전에는 완료 창을 닫거나 페이지를 새로고침하지 않는다.

| 요청 | 주소 | 하는 일 |
| --- | --- | --- |
| `POST` | `/home/api/work/migration/preview` | 기존 HOME 내보내기 JSON을 검사하고 DB와 비교. 저장하지 않음 |
| `POST` | `/home/api/work/migration/commit` | 검사한 백업·확인값·명시적 확인을 받아 새 기록만 저장 |

- 검사 응답의 `counts`는 자료 종류별 `new`·`same`·`conflict` 수다.
  충돌이 없으면 30분 동안 유효한 서명된 확인값(`token`)을 발급한다.
  확인값에는 원본 기록 대신 파일과 서버 상태를 비교할 수 있는 해시를 담는다.
- 저장 요청은 `{"backup":<원래 백업>,"token":<검사 확인값>,"confirmed":true}`다.
  검사 뒤 파일이나 대상 서버 기록이 바뀌면 다시 검사하도록 한다. 만료·변조된 확인값도 거부한다.
- 클라이언트 파일은 최대 2 MiB, 서버 요청은 최대 3 MiB, 전체 기록은 최대 5,000건이다.
  내보내기 형식·버전·업무 모드·기록 수·필드·날짜·중복 ID·캠페인 연결을 검사한다.
  파일 안에서 함께 옮길 새 캠페인과 업무의 연결도 허용한다. 모르는 필드는 버리지 않고 전체 작업을 거부한다.
- 기존 모델·입력 검사를 재사용한다. 업무의 빈 날짜는 DB에서 `NULL`로 대응하며,
  비교할 때 모델 기본값과 날짜 형식을 맞춘다. 화면 설정은 백업에 보존하고 DB로 옮기지 않는다.
- 공통 앱의 SQLite에서는 저장 시작부터 끝까지 다른 쓰기를 막고, 새 부모 캠페인을 먼저 저장한다.
  중간 오류나 최종 저장 오류가 나면 이번 요청 전체를 취소한다. 기존 기록에 덮어쓰기·삭제를 하지 않는다.
- 새 기록에만 `import_batch_id`를 표시한다. 같은 정규화된 기록 묶음에는 같은 이관 ID를 사용한다.
  결과 파일에는 이관 ID, 원본 확인값, 실제 추가한 ID와 최초 수정 번호를 담는다.
  이미 같은 내용으로 저장되어 있던 기록의 이관 표시는 바꾸지 않는다.
- 통신이 끊기면 저장되지 않았다고 단정하지 않는다. 같은 파일을 다시 검사해 서버 상태를 확인한다.
  같은 기록은 건너뛰므로 같은 파일을 다시 실행해도 중복으로 늘어나지 않는다.
- **브라우저 원본·백업 파일은 수정하거나 삭제하지 않는다.** 예시 파일은 이관하지 않는다.
  4단계 연결 이후에는 이관 완료 시 서버 기록을 다시 불러오고, 이후 내 업무 편집도 서버에 저장한다.

되돌리기가 필요하면 원래 백업과 이관 결과 파일을 먼저 확인한다. 해당 이관 묶음에서 실제 추가한 행인지,
수정 번호와 내용이 그대로인지, 나중에 생긴 연결이 없는지 점검한 뒤 별도 계획을 보고하고 승인받는다.
조건이 맞지 않으면 삭제하지 않고 멈춘다. 자식 기록부터 취소하는 방식으로 계획하되 기존 기록·DB 전체를 지우지 않는다.
이번에는 되돌리기 자동 실행 API를 만들지 않았다.

  실제 DB를 준비하지 않은 기존 서버는 이 표시를 보내지 않으므로, 새 JS가 열려도 기존 업무 편집을 계속할 수 있다.
  예시 모드에서는 서버와 별개로 시험할 수 있다. 종류별 색·꾸미기는 마지막 디자인 작업으로 미룬다.
- 사용자 승인 후 실제 DB에 칸을 추가했다. `init-db`는 기존 테이블에 새 칸을 추가하지 않으므로
  아래 전용 명령을 사용했다. 기존 DB를 삭제하거나 다른 테이블의 구조를 바꾸지 않았다.

```powershell
# 확인만: 기록과 구조를 바꾸지 않음
.venv/Scripts/python.exe -B -m flask --app app home tasks-add-category

# 실제 추가: 사용자 승인 후 기존 서버를 종료하고 실행 완료
.venv/Scripts/python.exe -B -m flask --app app home tasks-add-category --apply
```

- 명령은 HOME 업무 테이블에 칸 하나만 추가한다. 기존 업무의 나머지 값과 다른 테이블은 바꾸지 않는다.
  업무 수와 기존 칸이 그대로인지 확인하고, 오류가 나면 해당 변경을 취소한다.
  이미 같은 칸이 있으면 다시 추가하지 않으며, 다른 구조나 허용하지 않은 값이 있으면 변경 없이 중단한다.
- 실제 적용은 미리보기 확인 → 사용자 승인 → 기존 서버 종료 → `--apply` → 기록 보존 확인 → 서버 하나만 시작 순서다.
  CLI 실행 시 `.env` 자동 읽기와 Python 캐시 생성을 끈다. PM1에게는 칸 추가 결과를 공유한다.
- 검사: 합성 자료·메모리 SQLite로 **25개 모델·DB 준비·API 검사 통과**.
  기존 값 보존, 기본 명령은 확인만 수행, 재실행 안전성, 오류 시 취소, 종류 저장·재조회, 잘못된 값 거부,
  이전 백업의 미지정 처리, 수정 충돌 방지와 이관 표시 보존을 확인했다.
- 실제 HOME JS·템플릿과 설치된 `jsdom`으로 **23개 화면 검사 통과**.
  이전 서버와의 호환, 종류 선택·재조회·목록 표시, 복제·재계획 시 보존, 백업 포함과 예시의 브라우저 저장을 확인했다.
  시험 파일은 프로젝트 밖 임시 위치에서 사용하고 제거했다. 새 라이브러리·환경변수·CSS 변경은 없다.
- 코드 준비 시험 때는 실제 DB 파일 해시가 동일했다. 이후 사용자 승인으로 기존 프로젝트 서버를 종료하고
  명령의 확인 모드와 `--apply`를 순서대로 실행했다. 두 명령 모두 종료 코드 0이었다.
  기존 업무의 category를 제외한 모든 값과 다른 테이블의 모든 행은 적용 전후 확인값이 같았다.
  기존 업무 26개 모두 category가 빈 문자열(미지정)이며 이벤트 3개·업무 26개를 그대로 조회했다.
- `.env` 자동 읽기와 Python 캐시 생성을 끄고 서버를 `--debug --no-reload --no-debugger`로 하나 시작했다.
  HOME 화면·실제 저장 API의 `task_categories_enabled: true`·종류 선택 스크립트 제공을 조회로 확인했다.
  실제 업무의 종류를 바꾸는 시험은 하지 않았다. Python·JavaScript 문법 검사와 `git diff --check`는 통과했다.

### 4순위 — 외부 연동 보완

- 번역 결과는 서버 메모리에만 있어 서버를 끄면 사라진다. 자주 쓰는 제목이 많아지면
  파일이나 DB에 저장하는 방안을 검토한다. 무료 한도(월 50만 자) 보호가 목적이다.
- 검색어(`home/news_search.py`의 `PRESETS`)는 써 보면서 계속 다듬는다.
- 정부 공지 원문은 RSS가 확실하지 않아 지금처럼 사람이 확인한다.

  형식 검사 통과가 사실성이나 최신성의 보증을 뜻하지는 않는다. 기존 JSON·DB는 수정하지 않았다.

  2026-12-04~06과 [행사 사이트](https://danangchristmasmarket.com/vi/)의 2026-12-03~06이 달랐다.
  행사 사이트 본문에는 2025년 설명도 남아 있었다. 날짜를 임의로 고르지 않고 보류한다.
- DIFF 2027과 봄 공휴일의 구체 일정은 이번 검색에서 새 공식 확정 근거를 확보하지 못했다.
  미개최나 변경 없음으로 단정하지 않는다. 망고 시즌은 산지·품종을 특정한 근거가 필요하므로 전국 단일 날짜를 만들지 않는다.

  신문 보도는 10월 말 개최 예정·대상 분야를 확인할 수 있었지만 10월 28~30일의 직접 근거를 대체하지는 못한다.
  원래 날짜를 바꾸거나 재검증 완료로 표시하지 않고, 공식 원문의 재열람을 후속 확인으로 남긴다.

  2026-01-01 이전 제품에 관한 경과 규정이 있다. 적용 제외·경과 규정을 포함한 문구 보완은 담당자의 원문 확인과 별도 등록 승인 대상이다.

### 실행 방법

```
.venv/Scripts/python.exe -m flask --app app run --debug
```

`--debug`가 없으면 화면 파일이 캐시되어 수정이 반영되지 않는다.
서버를 켜기 전에 기존 서버를 반드시 끈다. 여러 개가 같은 포트에 뜨면 옛 화면이 섞여 나온다.
`.env`를 바꾸면 `--debug`로도 다시 읽지 않으므로 서버를 껐다 켠다.

관리 명령은 두 방식 모두 동작한다.

```
flask --app app home news-fetch --url <https 주소>
python -B -m home.news_import fetch --url <https 주소>
```
